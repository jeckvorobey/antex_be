## Context

Backend уже содержит реферальную модель и поля, связанные с referral_code и referral_rate/referral_rate_percent. Для админки нужно не просто показывать эти данные, а надежно массово закрывать пользователей с `referral_code = null` и отдавать предсказуемый контракт для UI.

## Goals / Non-Goals

**Goals:**
- Массово генерировать реферальные коды только для пользователей с `null`.
- Сохранять коды в БД и гарантировать уникальность.
- Отдавать admin-интерфейсу данные, нужные для кнопки и таблицы.
- Сохранить совместимость с уже существующими referral-потоками.

**Non-Goals:**
- Менять логику начислений или формулы процентов.
- Переписывать пользовательский referral flow целиком.
- Делать визуальный дизайн админки на backend-уровне.

## Decisions

1. **Массовая генерация будет работать только по `referral_code IS NULL`.**
   - Это исключает перезапись существующих кодов.
   - Альтернатива: пересчитывать всем пользователям. Отклонено, потому что это ломает ссылочную целостность и историю.

2. **Уникальность кода проверяется на уровне сервиса и БД.**
   - Сервис должен повторять генерацию при коллизии, а БД — защищать уникальным ограничением.
   - Альтернатива: полагаться только на случайность генератора. Отклонено, потому что при массовой операции это слабее, чем явная защита.

3. **Admin получает явный признак доступности массовой генерации.**
   - Видимость кнопки должна зависеть от наличия хотя бы одного пользователя с `referral_code = null`.
   - Альтернатива: вычислять это только на клиенте через таблицу. Отклонено, потому что backend должен быть источником правды.

4. **Табличный контракт будет включать referral code, referral rate percent и balance как отдельные поля.**
   - Это упрощает рендер в разных версиях таблицы и снижает риск дублирования вычислений на фронте.
   - Альтернатива: собирать все из разрозненных endpoint’ов. Отклонено из-за сложности и риска несоответствий.

## Risks / Trade-offs

- [Массовая генерация может затронуть много записей] → добавить тесты на частичный успех и повторный запуск.
- [Коллизия кода при высокой плотности данных] → retry-генерация и уникальный индекс.
- [UI может ожидать старый формат ответа] → сохранить совместимые схемы и добавить явные новые поля.

## Migration Plan

1. Уточнить backend-сервис генерации referral_code.
2. Добавить/обновить endpoint для массовой генерации и выдачи признака доступности.
3. Обновить схемы ответа для admin таблицы.
4. Добавить тесты на `null`, уникальность и неизменность существующих кодов.
5. Передать контракт в admin и дизайн-задачи.

Rollback: отключить вызов массовой генерации в admin UI и оставить существующие пользовательские referral-потоки без изменений.
